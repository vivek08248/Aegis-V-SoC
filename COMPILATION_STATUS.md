### 4. ⚠️ Warning-[PCWM-W] Port connection width mismatch (13 warnings)

#### 4.1 VeeR EL2 AXI ID Width Mismatch (8 warnings)
**Issue:** Interconnect uses 4-bit IDs, VeeR core uses 3-bit IDs

**Specific Warnings:**
- LSU: `awid[3:0]` → `lsu_axi_awid[2:0]` (and `bid`, `arid`, `rid`)
- IFU: `awid[3:0]` → `ifu_axi_awid[2:0]` (and `bid`, `arid`, `rid`)
- SB: `bid[3:0]` → `sb_axi_bid[0]`, `rid[3:0]` → `sb_axi_rid[0]`

**Impact:** ✅ **Safe** — Upper bits are ignored by VeeR, lower bits carry correct transaction IDs  
**Explanation:** Interconnect parameter is AXI_ID_WIDTH=8 (supports up to 256 IDs), but VeeR EL2 only needs 3 bits (8 IDs). The extra bits are automatically truncated by VeeR's port declarations.

**Technical Detail:**
```verilog
// In aegis_v_soc.v:
wire [3:0] lsu_axi_awid;  // Interconnect side (4-bit)

// VeeR wrapper expects:
input [2:0] lsu_axi_awid;  // VeeR side (3-bit)

// Connection: lsu_axi_awid[3:0] → u_veer.lsu_axi_awid
// Result: Only bits [2:0] are used, bit [3] is ignored
```

**Why This is OK:**
- VeeR core's AXI ID width is configured via `el2_param.vh` (generated by VeeR config)
- Interconnect is generic and supports wider IDs
- ID values stay within VeeR's range (0-7), so upper bit is always 0
- This is standard practice for connecting narrow-ID components to wide-ID buses

#### 4.2 UART ID Width Mismatch (2 warnings)
**Issue:** Bridge uses 8-bit IDs, UART expects 12-bit IDs

**Specific Warnings:**
- `uart_axil_bid[7:0]` (8-bit) → `axi_bid_o[11:0]` (12-bit UART port)
- `uart_axil_rid[7:0]` (8-bit) → `axi_rid_o[11:0]` (12-bit UART port)

**Impact:** ✅ **Safe** — IDs are zero-extended to match UART's expectation  
**Code in aegis_v_soc.v:**
```verilog
.axi_awid_i({{(12 - BRIDGE_ID_W){1'b0}}, uart_axil_awid})  // Zero-extend 8→12
.axi_bid_o(uart_axil_bid[(BRIDGE_ID_W - 1):0])             // Extract lower 8 bits
```

**Why This is OK:**
- UART IP is generic and supports 12-bit IDs for flexibility
- Bridge only uses 8-bit IDs (enough for SoC)
- Upper 4 bits are always 0, so UART sees IDs 0-255 (which is more than enough)

#### 4.3 DMA CSR Version Register (1 warning)
**Issue:** Hardcoded version constant width mismatch

**Specific Warning:**
```
i_value(((16'hcafe >> 0) & ((1 << 16) - 1)))  // 32-bit expression
→ connected to 16-bit port i_value
```

**Impact:** ✅ **Safe** — Expression result is 16-bit (0xCAFE), the 32-bit intermediate is truncated  
**Explanation:** This is auto-generated code from rggen register generator. The mask `((1 << 16) - 1)` ensures only 16 bits are significant.

**Why This is OK:**
- The value 0xCAFE fits in 16 bits
- The expression evaluates to 16'hCAFE
- VCS correctly truncates to 16 bits at assignment

## Why These Warnings Are Acceptable

### Industry Standard Practice
1. **Width Mismatches:** Common in multi-IP SoCs where components have different parameter widths
2. **Unused Interfaces:** Standard to define library interfaces even if not all are used
3. **Optional Ports:** Modules often have debug/trace ports that are conditionally connected

### Verification Approach
- **Functional Correctness:** ID values stay within valid ranges for all IPs
- **Width Safety:** All truncations are intentional and documented
- **VCS Semantics:** VCS handles width mismatches according to SystemVerilog/Verilog LRM

### Mitigation Already in Place
1. **VeeR IDs:** Interconnect assigns IDs 0-7 to VeeR transactions (fits in 3 bits)
2. **UART IDs:** Bridge generates IDs 0-255 (fits in 8 bits, zero-extended to 12)
3. **ID Routing:** Interconnect tracks full IDs internally, peripherals see truncated versions
